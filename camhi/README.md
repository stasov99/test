# CamHi: качественное видео онлайн и непрерывная запись в облако

Для **своих** камер, которые ты настраиваешь через приложение CamHi / CamHiPro.

Цель: забирать видео в максимальном качестве онлайн и непрерывно писать его в
облако.

Коротко: **само приложение CamHi для этой задачи не нужно**. Почти все
CamHi-камеры с питанием от сети отдают стандартный RTSP и ONVIF по локальной
сети. Их видео забирает небольшой компьютер рядом с камерами (Raspberry Pi,
мини-ПК, NAS) и складывает в облако. Разбирать приложение имеет смысл только
для камер, у которых RTSP нет (часть батарейных и 4G-моделей).

---

## 1. Как устроена связка «камера ↔ CamHi»

| Компонент | Что это |
|---|---|
| Камера | «Белая» IP-камера на SoC HiSilicon (Hi3516/Hi3518), Ingenic, Anyka и т.п. Прошивка от Shenzhen Hichip. |
| UID | Строка вида `XXXX-123456-ABCDE`. Нужна только приложению для P2P-доступа через интернет без проброса портов. Для нашей задачи не используется. |
| Приложение CamHi/CamHiPro | Клиент. Общается с камерой двумя путями: напрямую по локальному IP (ONVIF/RTSP/HTTP-API) и через облачный P2P-релей Hichip, когда ты не в одной сети. |
| Прошивочный веб-API | HTTP CGI на камере: `http://<ip>/cgi-bin/hi3510/param.cgi?cmd=...`. Отдаёт/меняет настройки, в т.ч. параметры RTSP. |

Вывод: для «забрать картинку и писать в облако» мы работаем **напрямую с
камерой по локальной сети**, минуя приложение и облако Hichip.

## 2. Самый простой и надёжный путь — RTSP + ONVIF

### 2.1. Найти камеру и проверить API

```bash
# IP камеры обычно видно в приложении CamHi: Settings → Device Info,
# либо на роутере в списке клиентов. Проверка, что это Hichip-прошивка:
curl "http://<ip>/cgi-bin/hi3510/param.cgi?cmd=getserverinfo" -u admin:<pass>
```

### 2.2. RTSP-ссылки (типичные для Hichip)

```
# Основной поток (высокое качество):
rtsp://admin:<pass>@<ip>:554/11
# Субпоток (низкое качество):
rtsp://admin:<pass>@<ip>:554/12
```

У части моделей путь другой (`/live/ch0`, `/ch0_0.h264`, порт 8554/10554).
Точный путь удобнее всего узнать через ONVIF, а не угадывать.

### 2.3. ONVIF — универсальный способ получить ссылку и управлять

ONVIF сам отдаёт RTSP-URI, профили, разрешение, PTZ. Проверка:

```bash
pip install onvif-zeep
python3 scripts/onvif_probe.py <ip> <port=8080|80> admin <pass>
```

Скрипт лежит в `scripts/onvif_probe.py`.

### 2.4. Выжать максимум качества

Через веб-API или ONVIF поднять битрейт/разрешение основного потока до
максимума, который поддерживает сенсор (часто 2K/4MP/5MP, H.265):

```bash
# Пример: выставить параметры основного потока (имена cmd зависят от прошивки,
# сверяйся с ответом getvencattr):
curl "http://<ip>/cgi-bin/hi3510/param.cgi?cmd=getvencattr&-chn=11" -u admin:<pass>
curl "http://<ip>/cgi-bin/hi3510/param.cgi?cmd=setvencattr&-chn=11&-bps=4096&-fps=25&-gop=50&-brmode=cbr" -u admin:<pass>
```

## 3. Непрерывная запись в облако

Идея: локальный «мост» тянет RTSP и одновременно
(а) отдаёт онлайн-поток куда нужно и (б) пишет сегментами в облачное хранилище.

### Вариант A. go2rtc + ffmpeg (лёгкий, рекомендую начать с него)

- **go2rtc** — ретранслятор: один RTSP с камеры раздаёт по WebRTC/HLS/RTSP
  множеству клиентов без перегрузки камеры. Онлайн-картинка в браузере.
- **ffmpeg** в режиме `segment` — режет поток на файлы по N минут, не
  перекодируя (`-c copy`, нулевая нагрузка), и их забирает синхронизация в
  облако. Конфиг и сервис — в `recorder/`.

### Вариант B. Frigate / Shinobi / MediaMTX

Готовые NVR-ы: принимают RTSP, пишут 24/7, имеют веб-UI, детекцию движения,
экспорт. Frigate умеет писать на любой диск, который дальше синхронится в
облако.

### Куда писать в облако

1. **Сегменты файлов → объектное хранилище** (S3 / B2 / GCS / Я.Облако):
   `rclone mount` или `rclone copy` по cron. Самый дешёвый и надёжный способ
   непрерывной записи. Пример юнита — `recorder/`.
2. **Готовый облачный VSaaS** (который умеет принимать RTSP-push или
   RTMP/SRT): локальный мост делает `ffmpeg … -f flv rtmp://...`.
3. **Облачное хранилище самой камеры в CamHi** — платное, закрытое, только
   по движению, качество и доступ к файлам ограничены. Для «непрерывно и
   качественно» не подходит.

## 4. Камеры без RTSP (батарейные / часть 4G) — когда нужен разбор приложения

У энергосберегающих моделей RTSP-сервер часто выключен (камера «спит» и будит
стрим только в приложении через P2P). Варианты по возрастанию сложности:

1. **Проверить, нельзя ли просто включить RTSP/ONVIF** в настройках камеры или
   скрытым CGI-вызовом — часто сервер есть, но отключён.
2. **Сменить прошивку на открытую (OpenIPC)** — если SoC поддерживается
   (HiSilicon, Ingenic, SigmaStar и др.). Тогда появляется полноценный
   RTSP/ONVIF, и камера становится обычной. Это самый «правильный» путь для
   таких моделей, но требует вскрытия и риска окирпичивания.
3. **Разобрать P2P-протокол (отладка приложения)** — см. раздел 5. Это нужно
   только если RTSP включить нельзя и прошивку не сменить.

---

## 5. Как «подебажить» приложение CamHi (для своих камер)

Цель отладки — понять, как приложение получает поток, чтобы повторить это без
приложения. Делается на своём устройстве и своей камере.

### 5.1. Сначала — локальный трафик (проще всего)

```bash
# Зеркалируем трафик камеры на роутере/свитче или снимаем на мосту:
nmap -p 80,554,8000,8080,8899,34567 <ip>      # открытые порты
# RTSP-рукопожатие видно сразу:
ffprobe -rtsp_transport tcp "rtsp://admin:<pass>@<ip>:554/11"
```

Если камера в принципе отдаёт RTSP/ONVIF — дальше приложение не нужно.

### 5.2. Если только P2P — смотрим, что делает приложение

- **Android + Frida/объективный анализ APK.** На своём телефоне с root/эмуляторе
  снять трафик (камера общается по UDP, порт релея Hichip ~32100, затем прямой
  UDP с камерой). Инструменты: `mitmproxy` для HTTP, `tcpdump`/Wireshark для
  UDP, Frida для перехвата вызовов нативной P2P-библиотеки внутри приложения.
- Протокол этого класса камер — семейство **PPPP/CS2** (та же база, что у
  Hichip). Есть открытые реализации-ретрансляторы для похожих камер, их можно
  изучить как референс (например проект `cam-reverse` для PPPP-камер). Это
  исследовательский путь, требует времени и навыков в реверсе.

### 5.3. Что сохранить при отладке

`frida/` — заготовки скриптов-перехватчиков. `scripts/analyze_apk.sh` —
распаковка APK и поиск нативных P2P-библиотек и строк протокола.

## 6. Рекомендованный план

1. Определи модель: питание от сети или батарейная/4G.
2. **Сетевая камера** → RTSP/ONVIF (раздел 2) + go2rtc/ffmpeg-segment + rclone
   в облако (раздел 3). Это закрывает задачу на 90% случаев.
3. **Батарейная/4G без RTSP** → попробуй включить RTSP, затем OpenIPC, и только
   в крайнем случае реверс P2P (разделы 4–5).

Перед реверсом стоит сначала проверить вариант 2 на конкретной камере — часто
RTSP уже работает, и городить разбор приложения не придётся.

---

> Всё это — для камер, которыми ты владеешь и управляешь. Доступ к чужим
> устройствам (включая перебор UID) незаконен и здесь не рассматривается.

## 7. Конкретный случай: камеры от сети, только 4G, SIM Yota

Вводные закрывают часть вариантов:

- **Питание от сети** → круглосуточная запись физически возможна (аккумулятор не
  ограничивает).
- **Только 4G, без WiFi/Ethernet** → подключить камеру к своей локальной сети
  нельзя. Значит, разделы 2–3 (локальный RTSP/ONVIF рядом с камерой)
  **неприменимы**.
- **Yota** → у обычной SIM физлица сеть за **CGNAT**, и белый внешний IP в LTE
  Yota практически не выдаёт (по техусловиям сети). Значит, достучаться до
  камеры снаружи по RTSP/ONVIF **нельзя**: входящих соединений нет.

### Главное следствие

Единственный канал к камере — тот же **исходящий P2P**, которым пользуется само
приложение CamHi (камера сама звонит на релей Hichip, клиент цепляется через
него). Всё решение строится вокруг этого. Важный плюс: P2P работает из любой
точки с интернетом, поэтому **компьютер-рекордер не обязан стоять рядом с
камерой** — он может быть дома или на VPS и обслуживать все камеры сразу.

### Что проверить в первую очередь (30 секунд, может всё упростить)

В веб-интерфейсе камеры / расширенных настройках CamHi поискать пункт
**RTMP / Push / Platform / «трансляция на сервер»**. Если он есть — камера сама
будет толкать поток на твой приёмник (MediaMTX/SRS/nginx-rtmp на VPS), и тогда
онлайн и запись 24/7 решаются без реверса и без возни с оператором. У дешёвых
Hichip-4G такого пункта обычно нет, но проверить стоит.

### Путь A — прагматичный, работает сегодня (рекомендую начать с него)

Готовый клиент Hichip на всегда включённом мини-ПК/VPS, который тянет
основной поток по P2P и пишет 24/7, плюс выгрузка в облако:

1. Поднять всегда-онлайн машину (мини-ПК дома или облачный Windows-VPS).
2. Поставить вендорский клиент: **CamHi/CamHiPro** (через Android-эмулятор) или
   **HiP2P Client / CMS** для Windows. Добавить камеры по UID.
3. Включить непрерывную запись основного потока на диск (в HiP2P — раздел
   «Запись/Record Management»; расписание в нём капризное, при проблемах пишем
   постоянно, без расписания).
4. `rclone` синхронит папку записи в облако (см. `recorder/record-to-cloud.sh` —
   логику выгрузки/ротации можно взять оттуда, источник — папка клиента).

Плюсы: без реверса, без смены SIM, запускается сразу, качество = основной поток.
Минусы: нужен работающий GUI-клиент 24/7, зависимость от релея Hichip, запись по
расписанию в CMS неудобная.

### Путь B — headless, кастомный (это и есть «разбор приложения»)

Повторить P2P-протокол (семейство **PPPP/CS2**) своим кодом и писать поток в
ffmpeg без всякого GUI:

1. Снять, как приложение общается с камерой (Frida + анализ нативной библиотеки,
   `frida/hook_p2p.js`, `scripts/analyze_apk.sh`; UDP-трафик к релею ~порт 32100
   и далее прямой UDP с камерой).
2. Собрать headless-клиент (как референс — открытые реализации PPPP для похожих
   камер; часть P2P-транспортов есть в go2rtc).
3. ffmpeg пишет полученный поток сегментами в облако (`recorder/record-to-cloud.sh`).

Плюсы: полностью автоматизируемо, без GUI, один процесс на сервере. Минусы:
трудоёмкий реверс, требует навыков, протокол недокументирован.

### Путь C — сменить SIM (если это вариант)

Обычная Yota не даст белый IP. Но **M2M/IoT-симка с белым статическим IP или
VPN-APN** (у Yota для юрлиц или у стороннего M2M-провайдера) вернёт прямую
доступность камеры → снова работают RTSP/ONVIF и вся простая схема из разделов
2–3. Технически самый чистый путь, если замена SIM/тарифа допустима.

### Отдельно про качество на 4G

Через P2P идёт тот же основной поток, что и по RTSP, — разрешение/битрейт те же.
Но реальный потолок задаёт **скорость отдачи (upload) 4G** в точке установки:
если основной поток 4 Мбит/с, а аплинк слабый/нестабильный — будут рассыпания и
задержки. Это ограничение не метода, а канала; при слабом 4G, возможно, придётся
чуть снизить битрейт ради стабильности.

### Моя рекомендация по приоритету

1. Проверить RTMP/Push в камере → если есть, это лучшее решение.
2. Если нет → **Путь A** (вендорский клиент + rclone) как рабочее решение сейчас.
3. Параллельно, если нужен headless и полный контроль → **Путь B** (реверс P2P).
4. Если допустима смена SIM на M2M с белым IP → **Путь C**, тогда всё становится
   тривиально.

## 8. Финальный план под конкретику: 3× PS-Link 4G, SIM у каждой, аплинк 4–5 Мбит/с

PS-Link GBT/GBK — это Hichip-камеры под CamHi (до 5 Мп, microSD). RTMP-push в
их прошивке, скорее всего, нет (проверь всё же меню камеры), поэтому берём
**Путь A**: одна всегда-онлайн машина тянет все 3 камеры по P2P и пишет 24/7,
`rclone` льёт в облако с ротацией.

### Что подтвердилось по факту (меню камеры, UID SSAU-...)

- UID начинается на **SSAU** → P2P-камера семейства PPPP/CS2, канал только
  исходящий P2P. Подтверждает выбор Пути A.
- **RTMP/Push в меню нет** → камера сама поток на сервер не отдаёт.
- Есть **FTP** — но заливает только снимки/клипы по тревоге, не непрерывный
  основной поток. Годится лишь как резерв по событиям.
- Есть **Wi-Fi** — запасной путь: если на точке появится локальная сеть, камеру
  можно увести в WiFi и получить локальный RTSP (тогда работает простая схема
  из разделов 2–3).
- **Расписание записи + SD** — локальная запись на microSD в камере, полезна как
  подстраховка при обрыве 4G (не облако).
- Битрейт/разрешение/кодек задаются в **«Видео настройки»** (см. таблицу ниже).

### Финальные решения

- **Рекордер — домашний мини-ПК** (есть у пользователя, 24/7, бесплатно). VPS не
  используем под хранение — дорого.
- **Облако — дешёвое объектное хранилище** (см. блок «объём и стоимость» ниже).

### Схема

```
camera1 (SIM) ─┐
camera2 (SIM) ─┤  P2P-релей Hichip   ┌─ рекордер (мини-ПК/VPS, 24/7)
camera3 (SIM) ─┘  (исходящие от камер) └─ пишет на диск → rclone → облако
```

Рекордер может стоять где угодно с интернетом — у камер он быть не обязан.

### Настройка камер (через CamHi, один раз на каждую)

Основной поток под аплинк 4–5 Мбит/с — ставим с запасом на стабильность:

| Параметр | Значение |
|---|---|
| Кодек | **H.265** (вдвое экономнее H.264) |
| Разрешение | 2K/4Мп (или 5Мп, если канал держит) |
| Битрейт | **2000–3000 кбит/с**, режим **CBR** |
| FPS | 15–20 (для наблюдения достаточно, меньше рассыпаний) |
| GOP/I-frame | 2× от FPS (напр. 40) |

4–5 Мбит/с аплинка на поток 2–3 Мбит/с — комфортный запас.

### Рекордер (Путь A, два варианта машины)

**Вариант 1 — Windows (проверенный для Hichip):** мини-ПК дома или облачный
Windows-VPS. Ставим **HiP2P Client (CMS)**, добавляем 3 камеры по UID, включаем
запись основного потока на диск. Папку записи синхронит `rclone` (скрипт
`sync-to-cloud.ps1`-аналог: тот же `rclone move` + ротация, что в
`sync-to-cloud.sh`, через Планировщик задач каждые 5 мин).

**Вариант 2 — Android-эмулятор:** если удобнее сам CamHi/CamHiPro — поднять его
в эмуляторе на той же машине, включить запись, дальше — тот же rclone.

Запись и выгрузка:
1. `cp recorder/cameras.example.env recorder/cameras.env` и заполнить UID/пароли.
2. Настроить облако: `rclone config` (S3/B2/Я.Облако — любой).
3. `REC_DIR=<папка_записи_клиента> recorder/sync-to-cloud.sh` по cron каждые
   5 мин (Linux) или Планировщик задач (Windows). Ротация хранения — через
   `RETENTION_DAYS` в `cameras.env`.

### Без облака: запись на локальный диск мини-ПК (самый дешёвый вариант)

«Облако» в задаче — лишь способ хранить непрерывную запись. Раз мини-ПК и так
работает 24/7, можно писать **прямо на его диск** и не платить за облако вообще.
Онлайн-просмотр при этом не теряется (он идёт по P2P через приложение или через
рекордер), облако нужно было только для хранения файлов.

Что меняется:
- Вместо `rclone` в облако — рекордер (HiP2P / CamHi / ffmpeg) пишет в папку на
  локальном (или внешнем USB) диске.
- Ротация — чистим старые файлы на диске по расписанию (скрипт
  `recorder/rotate-local.sh`), чтобы диск не переполнился.

Сколько места нужно (3 камеры, ~2,5 Мбит/с, ~81 ГБ/сутки суммарно):

| Глубина архива | Нужно на диске |
|---|---|
| 7 дней | ~0,6 ТБ |
| 14 дней | ~1,1 ТБ |
| 30 дней | ~2,4 ТБ |
| 60 дней | ~4,9 ТБ |

То есть одного диска **4 ТБ хватит примерно на 50 дней**, 8 ТБ — на ~100 дней.
Разовая покупка диска вместо ежемесячной платы за облако.

Единственный минус против облака — нет офсайт-копии: если с мини-ПК что-то
случится (поломка/кража/пожар дома), архив потеряется. Подстраховка —
оставить включённой запись на **SD-карту в самой камере** (она на объекте, т.е.
копия в другом месте), либо периодически копировать важное на второй диск.

### Путь B для этих камер (если захочешь headless без GUI)

Реверс P2P (разделы 4–5): свой клиент тянет поток и пишет ffmpeg-ом
(`recorder/record-to-cloud.sh`). Для 3 камер начинать с этого не стоит — Путь A
закрывает задачу быстрее; B имеет смысл как второй этап, если надоест GUI-клиент.

### Важно про объём и стоимость облака

Поток ~2,5 Мбит/с = **~27 ГБ/сутки с камеры**. 3 камеры = ~81 ГБ/сутки.
При ротации **14 дней** в облаке постоянно лежит **~1,1 ТБ** (не растёт).
Записывается (ingest) ~2,4 ТБ/месяц, но хранится именно ~1,1 ТБ.

Ориентир по цене за ~1,1 ТБ хранения (проверь на сайтах, цены меняются):

| Хранилище | Цена | Оплата | Заметка |
|---|---|---|---|
| **Backblaze B2** | ~$6,95/ТБ/мес → ~$8/мес | иностранная карта | дёшево, **без штрафа за раннее удаление** — идеально под ротацию |
| **Российский S3** (Timeweb/Яндекс) | ~1–1,5 ₽/ГБ/мес → ~1100–1600 ₽/мес | рубли | удобно по оплате, S3-совместимо |
| ~~Wasabi~~ | ~$8/ТБ + мин. 1 ТБ | — | **НЕ брать:** минимум хранения 90 дней — удалённое через 14 дней всё равно оплачивается как 90, ротация теряет смысл |

Практика:
- **обязательно** держать ротацию (`RETENTION_DAYS`) — иначе объём растёт без
  предела;
- для оплаты в рублях — российский S3 (Timeweb/Яндекс); для минимальной цены при
  иностранной карте — Backblaze B2;
- **Wasabi под короткую ротацию не подходит** (90-дневный минимум);
- хочешь ещё дешевле — часть камер перевести с 24/7 на запись по движению, или
  сократить хранение до 7 дней (~0,56 ТБ).
